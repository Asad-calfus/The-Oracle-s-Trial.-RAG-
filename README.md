# SmartDoc — Document Q&A using RAG

SmartDoc lets you upload a PDF and ask questions about it. It answers using
only the content of the uploaded documents, and always shows which
file/page the answer came from — it never invents an answer or a citation.

## Architecture

```
Upload flow:
  PDF -> extract text (per page) -> split into chunks -> embed each chunk
      -> store in ChromaDB (with source file, page, chunk_id metadata)

Question flow:
  Question -> embed -> find a WIDE pool of similar chunks in ChromaDB
      -> drop chunks that aren't similar enough (score filter)
      -> rerank the survivors, keep the true best few
      -> send those chunks + question to the LLM (strict prompt)
      -> return answer + citations (from chunk metadata, not the LLM)
```

Frontend (Streamlit) and backend (FastAPI) are two separate processes that
only talk over HTTP — the frontend never touches the database or the LLM
directly.

## Folder structure

```
backend/
  config.py       - all settings in one place (paths, models, thresholds)
  ingest.py       - PDF -> text -> chunks -> vector store
  vectorstore.py  - opens/writes to the Chroma vector database
  database.py     - PostgreSQL: chat threads and messages
  llm.py          - builds the shared LLM client (used by rag.py + reranker.py)
  reranker.py     - reorders candidate chunks by asking the LLM to judge relevance
  rag.py          - retrieval + hallucination checks + LLM call + citations
  main.py         - FastAPI app: /health, /upload, /documents, /threads, /query
frontend/
  app.py          - Streamlit UI, calls the backend over HTTP
data/
  documents/      - uploaded PDFs
  chroma/         - the persistent vector database (created on first use)
```

## Setup

1. Create and activate a virtual environment:
   ```
   python3 -m venv .venv
   source .venv/bin/activate
   ```
2. Install dependencies:
   ```
   pip install -r requirements.txt
   ```
3. Create the PostgreSQL database used for chat history (needs a running
   Postgres server):
   ```
   createdb smartdoc
   ```
4. Copy `.env.example` to `.env` and fill in your own values:
   ```
   OPENAI_API_KEY=sk-...
   DATABASE_URL=postgresql://YOUR_USER@localhost:5432/smartdoc
   ```

The `threads` and `messages` tables are created automatically the first time
the backend starts.

## Running

Start the backend (auto-restarts on code changes):
```
uvicorn backend.main:app --reload --port 8001
```

Start the frontend, in a separate terminal (with `.venv` activated again):
```
streamlit run frontend/app.py
```

Open the URL Streamlit prints, upload a PDF, then ask a question.

## How it works

- **Ingestion** (`ingest.py`): `PyPDFLoader` extracts text per page.
  `RecursiveCharacterTextSplitter` breaks each page into overlapping chunks
  (`CHUNK_SIZE` / `CHUNK_OVERLAP` in `config.py`). Each chunk is embedded
  with OpenAI's `text-embedding-3-small` and saved to ChromaDB along with
  its source filename, page number, and a chunk id.

- **Retrieval** (`rag.py`): the question is embedded the same way, and
  Chroma returns a wider pool of `RERANK_CANDIDATE_K` similar chunks, each
  with a distance score (lower = more similar) — wider than what's actually
  sent to the LLM, so a relevant chunk still has a chance even when many
  documents are competing for the same top spots.

- **Reranking** (`reranker.py`): that wider candidate pool is handed to the
  LLM directly, along with the question, and it's asked to pick out and
  order the truly most relevant ones (`RETRIEVAL_TOP_K` of them). This is
  more accurate than raw embedding distance alone, since the LLM actually
  reads each candidate against the exact question instead of just comparing
  vector positions.

- **Hallucination protection — two independent layers:**
  1. *Score filter*: chunks with a distance above
     `SIMILARITY_SCORE_THRESHOLD` are dropped before they ever reach
     reranking or the LLM.
  2. *Strict prompt*: the LLM is instructed to answer **only** from the
     given context, and to reply exactly `"I don't know based on the
     uploaded documents."` if the answer isn't there. This catches cases
     the raw distance score can't cleanly separate.

- **Citations**: filename and page number always come from the chunk
  metadata attached during ingestion — never generated by the LLM. This
  is what guarantees a citation can't be wrong or made up.

- **Chat threads** (`database.py`): questions and answers are stored in
  PostgreSQL, in a `threads` table and a `messages` table (one-to-many, with
  citations kept alongside each answer as JSONB). The frontend holds no chat
  state of its own — it reads threads and messages back from the API on every
  render, so conversations survive a page refresh.

## Tech stack

FastAPI, Streamlit, LangChain, ChromaDB, PostgreSQL, OpenAI
(`gpt-4o-mini` for answers and reranking, `text-embedding-3-small` for
embeddings).
